# Toolsets

A toolset is a named group of tools declared once at the top level and granted to an agent by naming it in the agent's `tools` list. Two kinds exist, selected by the toolset's `type` field: `simple` (the default when the field is absent) is a plain group of inline tool declarations plus references to other toolsets; `builtin` is a named bundle shipped inside blorb, selected by a `builtin` field (currently `file`, which bundles the `read` and `grep` builtins), configured by one shared `config` object at the toolset level - `base_dir` is written once, no per-member declarations exist, and members carry the builtins' own descriptions. A tool granted through a toolset is renamed with the toolset as a prefix, joined by a single hyphen: toolset `kb` containing tool `read` grants `kb-read`; a builtin toolset `kb` of kind `file` grants `kb-read` and `kb-grep`. The same leaf name may appear in several toolsets (`kb1`/`kb2` each containing `read` grant `kb1-read`/`kb2-read`). Toolsets nest by referring to other top-level toolsets of either kind, and prefixes compose along the grant path: toolset `dev` referring to toolset `clock`, which contains `read`, grants `dev-clock-read`, so granting `dev` and `clock` side by side yields `dev-clock-read` and `clock-read`. An agent's `tools` list names any mix of top-level tools, whole toolsets, and individual toolset members by granted name (`kb-read` pulls just that member); any redundancy is a config error, whether an exact repeat or a toolset granted alongside one of its own members. The hyphen separator is deliberate: tool names go verbatim to the LLM API as function names, and OpenAI and OpenAI-compatible servers that copy its validation reject anything outside `^[a-zA-Z0-9_-]{1,64}$` at request time; composed names also inherit that server's 64-character cap, which we document but do not police (it is OpenAI's limit, not a universal one). Because everything downstream of `config.AgentTools` (chat, run, subagents, judges, the registry, the engine's forced-tool check) consumes whatever names the resolution produces, the prefixing lives entirely in `internal/config` plus one small addition to the builtin package; no other package needs a behavior change - only tests.

## Commit 3: granting toolsets and members

> The previous commits added validated toolset declarations of both kinds; this commit lets agents grant them and computes the prefixed names. An agent's `tools` list names top-level tools, whole toolsets, and individual toolset members by granted name; any redundancy is an error. Everything downstream consumes granted names unchanged: chat (chat.go:150), run (run.go:137), subagents (subagent.go:52), and judges (judge.go:156) all build registries from `AgentTools`, and the engine's forced-tool check (engine.go:157-166) compares against the registry's definitions - a `forced_tool` naming a granted name works with no engine change.
>
> In `internal/config/config.go`:
>
> - New unexported expansion helper, e.g. `(c Config) expandToolset(ts Toolset, prefix []string, seen map[string]bool) ([]ToolEntry, error)`: walks `ts`'s members in declared order; a leaf entry is copied with `Name` rewritten to `strings.Join(append(prefix, leafName), "-")`; a toolset-ref entry appends the referenced toolset's name to `prefix` and recurses. For a builtin toolset the members are synthesized instead of declared: `builtin.ToolsetMembers(ts.Builtin)` yields the member `Builtin`s, and each becomes a copied `ToolEntry{Type: ToolTypeBuiltin, Name: member.Name, Description: member.Description, Builtin: member.Name, Config: append([]byte(nil), ts.Config...)}` - the leaf name is the member's own name, the description comes from the builtin (the config author writes none), and the shared raw config is copied per member. `prefix` starts as `[ts.Name]` for a top-level toolset, so `kb` (builtin, file) grants `kb-read`/`kb-grep` and `dev` -> `clock` -> `read` grants `dev-clock-read`. The `seen` set guards recursion so an unvalidated programmatic cycle cannot loop forever (a cycle grants nothing anyway - validation rejects it - but the helper must not hang).
> - New unexported reference-index builder, e.g. `(c Config) toolReferenceIndex() (map[string][]ToolEntry, error)`: expands every top-level toolset once and builds one map over the whole agent reference space - each top-level tool name, each toolset name, and every granted member name of every top-level toolset, mapping to the entry or entries it grants (a toolset name maps to its full expansion; a top-level tool name to its single entry; a granted member name to that one entry, `Name` already rewritten). A duplicate key anywhere is an error: `duplicate name %q (tools, toolsets, and toolset members share one reference space)` - this is the global uniqueness rule, and it also catches hyphen-composition collisions (toolset `a-b` containing `c` grants `a-b-c`, the same name as toolset `a` containing a ref to toolset `b` containing `c`; both paths produce keys in the map, so the collision is rejected whichever kind caused it).
> - In `Validate()`: call the index builder once after toolset validation (so a reference-space collision surfaces before any agent error), then pass the index into agent validation. Keep `default_agent` and the cycle checks last as today.
> - `Agent.validate` (config.go:727) takes the index instead of the raw tools list: `a.validate(models, toolsetsIndex)`. The per-reference loop (config.go:746-755) resolves each name against the index - an unresolvable name is `agent %q: unknown tool, toolset, or toolset member %q` (an empty entry gives the same message with `""`, replacing today's `unknown tool %q`). Drop the reference-level duplicate check; redundancy is detected on the granted set instead (next point), which subsumes it and keeps the existing message for the plain case.
> - New per-agent grant expansion, e.g. `(c Config) agentGrantedTools(a Agent, index map[string][]ToolEntry) ([]ToolEntry, error)`: walks `a.Tools` in listed order, appends the granted entries each reference maps to (in toolset declaration order for a toolset reference), and errors the moment a granted name is appended twice: `agent %q: duplicate tool %q`. This makes any redundancy a config error: an exact repeat (`echo`, `echo`), a toolset granted alongside one of its members (`kb`, `kb-read`), and two references whose expansions overlap.
> - In `Validate()`, inside the agents loop (config.go:582-590), run the grant expansion after `a.validate` so its errors surface (the duplicate-granted-name cases the reference-level rules cannot see, e.g. a top-level tool literally named `kb-read` granted alongside toolset `kb`).
> - `AgentTools` (config.go:522) becomes a thin wrapper: build the index (dropping the error, as today's comment already assumes a validated config), expand `a.Tools`, return the entries. Update its doc comment: the result carries the granted names (prefixed for toolset members), in the agent's listed order with toolset members expanding at the reference position in the toolset's declared order; as today, an unvalidated programmatically-built config may come up short, and the helpers' seen-set guards keep it from hanging.
> - `validateAgentCycles` (config.go:651): the `target` map keyed by top-level tool names no longer covers subagent tools inside toolsets or individually granted members. Rework the edges to come from grant expansion: for each agent, expand its granted entries and add an edge to each subagent entry's `Agent`; judge edges unchanged; messages unchanged.
> - Update doc comments that say agents list "top-level tools": `Agent` (config.go:114) and `Agent.Tools` (config.go:127-130) - an agent's `tools` names top-level tools, toolsets, and toolset members by granted name.
> - The tools package needs no change: granted entries are ordinary validated `ToolEntry` values (builtin toolset members carry a non-empty description from the builtin, so `newBuiltinTool`'s checks pass), each parsing the shared config independently - two members of one `file` toolset each open their own sandbox root on the same `base_dir`, exactly as two separately declared builtin entries do today.
