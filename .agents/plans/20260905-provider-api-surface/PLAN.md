# Providers, then the provider API surface: listing, sampling, format, tool choice, logprobs

Restructures the config first: provider-level facts (type, base_url, api_key_env) move out of `models` into a new top-level `providers` list, and models become `{name, provider, model_name}` referencing a provider — so several models can share one server declaration, and the connection is named. On that foundation the plan grows the provider API surface along the neutral-type extension path established by `reasoning_effort`: a `ModelLister` capability with a new `blorb models` command (Ollama `/api/tags`, OpenAI-compatible `/v1/models`); neutral sampling parameters, declared per provider (server-wide generation defaults), flowing through `llm.Request` — openai top-level, ollama nested in `options`; Ollama-only `format` (structured output) and `keep_alive`, validated against the model's provider type; `tool_choice` including forced-tool mode with engine behavior; and logprobs requested, decoded, and surfaced through `blorb run`. The engine consumes only neutral types throughout.

## Commit 1: Extract providers from models in the config

> Split connection-level facts out of `models` into a new top-level `providers` list. This is a breaking schema change — blorb is pre-1.0 and the schema is ours to reshape — so there is no back-compat path: every config, fixture, and test moves to the new shape in this one commit, and each test keeps its original intent.
>
> - In `internal/config/config.go`:
>   - Add `Provider`: `Name` (identity; models reference it by their `provider` field), `Type` (the existing `ModelTypeOpenAI`/`ModelTypeOllama` discriminators), `BaseURL`, `APIKeyEnv *string` (same pointer rule as before: explicit empty is an error, absent means no key). `validate()`: name required and matching `NamePattern`; base_url required, http/https with a host; api_key_env pointer rule. It carries no model-level fields.
>   - Reshape `Model` to `Name`, `Provider` (names a defined provider), `ModelName`, `ReasoningEffort` (unchanged semantics and validation — thinking is about the model, not the connection). The old `Type`, `BaseURL`, and `APIKeyEnv` fields are removed from Model. `validate()` takes the providers list: the named provider must exist, model_name is required, reasoning_effort is validated as today.
>   - `Config` gains `Providers []Provider` (`json:"providers"`), required and non-empty like models, with duplicate-name rejection. Add a `Config.Provider(name) (Provider, bool)` accessor mirroring `Config.Model`. Update `Validate()` ordering: providers validate first (models and the provider-type lookups depend on them), then models with providers in scope, then agents — agent validation is untouched (agents still reference models by name).
>   - `SupportedModelTypes()` stays; its error messages now come from provider validation ("unknown type" on a provider entry).
> - In `internal/chat/chat.go`: the `clientFactories` registry becomes keyed by provider type. Each factory takes the resolved `config.Provider` plus the model's `ModelName` and `ReasoningEffort` (connection from the provider, per-model fields alongside): the openai entry builds `openai.Config{BaseURL: provider.BaseURL, Model: modelName, APIKey: <env-resolved>, ReasoningEffort, Sink}`; the ollama entry likewise. `NewClientWithGetenv` resolves the agent's model, then that model's provider, then dispatches; unknown provider types error with the same "(supported: ...)" phrasing. Add `NewProviderClient(cfg config.Config, providerName string, getenv func(string) string, sink logging.Sink) (llm.Client, error)` for provider-scoped construction without a model (the `blorb models` command uses it next commit); it resolves the provider by name through the same registry.
> - Everywhere else: nothing reads the removed Model fields directly except chat and tests — grep for `\.Type`/`BaseURL`/`APIKeyEnv` on `config.Model` and fix call sites. `internal/run`, engine, tools, and prefactor consume `llm.Client` and agent-scoped config and should need no changes beyond config construction in tests.
> - Tests and fixtures: reshape every `internal/config/testdata` fixture (each `models` entry splits into a provider entry plus a `{name, provider, model_name}` model; `model_*` fixtures become `provider_*` for the connection-level rejections — bad base_url, empty api_key_env, unknown type — and model-level ones keep the `model_*` prefix: missing model_name, missing provider, unknown provider, duplicate provider names, bad reasoning_effort). Reshape the programmatic helpers in config, chat, run, and tools tests (`validModel`, `testModel`, `ollamaTestModel`, and friends) to build provider+model pairs. The chat tests' `writeBlorbConfig` helper writes the new shape. Keep every existing assertion's intent; only the construction changes. Add: a model naming an unknown provider is rejected; `Config.Provider` lookup present/absent.

## Commit 2: ModelLister capability and the blorb models command

> Add an optional client capability for enumerating the models a server has installed, and a command that uses it — now naturally per provider:
>
> - In `internal/llm/llm.go`: add `ModelInfo{Name string, ModifiedAt string, SizeBytes int64}` and the `ModelLister` interface: `ListModels(ctx context.Context) ([]ModelInfo, error)`. Document it as an optional capability: clients whose servers can enumerate their installed models implement it, and consumers type-assert, exactly like `StreamingClient`. `ModifiedAt` stays a string (server-formatted); servers without the notion leave fields zero.
> - In `internal/llm/ollama/client.go`: implement `ListModels` — GET `BaseURL + "/api/tags"`, bearer header when `cfg.APIKey` is set, honouring ctx. Decode `{"models":[{"name","modified_at","size"}]}` into `ModelInfo{Name, ModifiedAt, SizeBytes}`. Non-2xx: read the body with `io.LimitReader` up to `maxBodyLen` and return an error carrying the status and the UTF-8-safe truncated body (the `truncate` helper). Sort the result by name so display is deterministic.
> - In `internal/llm/openai/openai.go`: implement `ListModels` — GET `BaseURL + "/models"` (url.JoinPath off the trimmed base, mirroring `post`'s endpoint building), bearer when set. Decode the OpenAI list envelope `{"data":[{"id","created","owned_by"}]}` into `ModelInfo{Name: id}` (ModifiedAt and SizeBytes stay zero — OpenAI-compatible servers do not carry them). Same non-2xx handling and sorting by name.
> - In `main.go`: add a `models` subcommand following the chat/run wiring (flags: the existing config-path flag pattern). Iterate the config's providers; per provider print one block — name, type, base_url — then build a provider-scoped client via `chat.NewProviderClient` and, when it implements `llm.ModelLister`, fetch the server's installed models and print them, marking each of the provider's configured models `installed` or `NOT INSTALLED` by `model_name`. Env keys resolve through the same path as a real session; a missing key or a listing fetch failure is reported per provider and does not stop the others. Exit code: 0 when every provider that could be listed shows all its configured models installed; 1 when any listing failed or any model is missing (typo detection is the point). Usage line follows the existing command help style.
> - Tests: in `internal/llm/ollama/client_test.go`, httptest cases for `/api/tags` — happy path decodes and sorts, bearer header present when the key is set, non-2xx carries status and body snippet, `ModifiedAt`/`SizeBytes` populated. In `internal/llm/openai/openai_test.go`, the same for `/models` — `id` maps to Name, zero ModifiedAt/SizeBytes, non-2xx handling. For the command, follow however existing commands are tested in `main_test.go` and cover: a provider whose server lists its configured model (exit 0, `installed` shown), a typo'd model_name (exit 1, `NOT INSTALLED` shown), and a server that errors on the listing (exit 1, error reported, other providers still listed).

## Commit 5: Ollama format (structured output)

## Commit 7: tool_choice from config to wire, with engine forced-tool behavior

> Add tool-choice control. This is the one stage that changes engine behavior, not just wire shaping:
>
> - In `internal/llm/llm.go`: add `type ToolChoiceMode string` with `ToolChoiceAuto`/`ToolChoiceNone`/`ToolChoiceRequired`/`ToolChoiceForce` ("auto"/"none"/"required"/"force"), and `type ToolChoice struct { Mode ToolChoiceMode; ForceTool string }` (ForceTool meaningful only for force). `Request` gains `ToolChoice *ToolChoice` (nil = auto).
> - In `internal/config/config.go`: `Model` gains `ToolChoice string` (`json:"tool_choice,omitempty"`, default/absent = auto) and `ForcedTool string` (`json:"forced_tool,omitempty"`). Validation in `Model.validate()`: tool_choice must be one of the four modes; `forced_tool` is required when tool_choice is force and an error otherwise; `forced_tool` must match `NamePattern`. Models on both provider types support the knob (OpenAI and Ollama both carry tool_choice on the wire).
> - Wire mapping in both clients: auto omits the field entirely; none/required serialize as the bare string; force serializes as the OpenAI shape `{"type":"function","function":{"name":...}}` (Ollama accepts the same object form, so both clients build it identically). `wireRequest` in each package maps `req.ToolChoice`.
> - In `internal/engine`: `EngineConfig` gains `ToolChoice *llm.ToolChoice`, plumbed from the model entry exactly like `Sampling` (chat, subagent runner, and run mode; resolve the mode/force pair from the config fields at the same call sites). Engine behavior: at construction, force mode requires the forced tool to be among the registry's tools (error naming it otherwise). On each request the engine sets `ToolChoice`. After a response in force mode: if the message calls the forced tool, proceed normally (the engine executes it like any call); if the message carries no tool calls, treat it as a repairable deviation following whatever mechanism the engine already has for a model response that should have carried tool calls — and if none applies, fail the turn with a clear error naming the forced tool and what came back instead. None/required/auto need no engine logic beyond sending the field; document on `EngineConfig` that required means the server is asked to force some call and the engine does not police the result. Document on `ToolChoiceNone` why it exists despite no-tools agents already existing: `none` keeps the request prefix byte-identical to the conversation so far — tools stay advertised — so provider prompt caches (OpenAI prefix caching, vLLM, llama.cpp warm KV) keep hitting, where omitting the tool definitions would bust the cache; it forbids calls for a turn without paying the context reprocessing cost.
> - Tests: config fixtures for the mode set, the missing/extra `forced_tool` cases, and a bad name. Wire tests in both clients: auto omitted; none and required as bare strings; force as the object form. Engine tests: construction rejects a forced tool that is not granted; force mode proceeds when the fake returns the forced call; force mode takes the repair/error path when the fake returns plain text; the request carries the configured ToolChoice. Plumbing assertions in chat/run tests that the model entry's tool_choice reaches the engine.
>

## Commit 8: Logprobs end to end

> Add optional per-token log probabilities, requested from config, decoded into the neutral response, surfaced through run output:
>
> - In `internal/llm/llm.go`: `type TopLogprob struct { Token string; Logprob float64; Bytes []int }` and `type Logprob struct { Token string; Logprob float64; Bytes []int; Top []TopLogprob }`. `Response` gains `Logprobs []Logprob` (`json:"logprobs,omitempty"`).
> - In `internal/config/config.go`: `Model` gains `Logprobs bool` (`json:"logprobs,omitempty"`) and `TopLogprobs int` (`json:"top_logprobs,omitempty"`). Validation in `Model.validate()`: `top_logprobs` in [0, 20] (OpenAI's cap), and settable only when `logprobs` is true. Models on both provider types.
> - In both clients: `Config` gains `Logprobs bool` and `TopLogprobs int` (client-level, like ReasoningEffort — no per-request channel); the factories pass them. On the wire: openai sets `logprobs: true` and `top_logprobs` on the request; ollama sets `logprobs: true` and `top_logprobs` likewise (both are request fields Ollama's /api/chat accepts). Decode: openai's non-streaming response `choices[].logprobs.content` maps to `Response.Logprobs`; ollama's non-streaming `logprobs` array maps the same way (its field shapes: `token`, `logprob`, `bytes`, `top_logprobs[]` with `token`/`logprob`/`bytes`). Streaming paths ignore logprobs: document on each client's ChatStream that streamed logprob data is not decoded, and do not extend the stream accumulators.
> - In `internal/run`: extend the output. The ndjson format's response/done events include `logprobs` when present (inspect the existing event structs in `internal/run/ndjson.go` and follow their conventions). The plain format gains a `--logprobs` flag that, after the response body, prints one line per token: the token, its logprob, and — compactly — the top alternative when present. Without the flag, plain and chat output are unchanged. Chat gains no display.
> - Tests: config fixtures (valid pair, top_logprobs out of range, top_logprobs without logprobs). Both clients: a httptest response carrying logprobs decodes into the neutral shape (tokens, bytes, top alternatives); a request with the config set carries the wire flags; a request without omits them. Run: ndjson events carry logprobs; plain with the flag prints the block; plain without does not.
>
